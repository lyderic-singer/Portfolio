Overview

Trador is a fully asynchronous Python framework for perpetual exchanges. It gives one Exchange interface across venues, so a strategy is written once and runs unchanged everywhere. I designed every layer: the exchange engines, the adapters, the strategy toolkit, the infrastructure and the control interface.

Running it with real money taught me what decides whether an edge survives: fees, latency, adverse selection, and staying up when an exchange API fails. I moved the servers twice, from Germany to France and then to Japan, to get closer to the exchanges.

The public repository is a showcase of the refactored framework with one example strategy. The production strategies (market making, funding, arbitrage, HIP-4 outcomes), their hedge engine, parameters and research tools stay private.

Strategy families

market making
Quotes both sides and earns the spread, with inventory and adverse-selection control.
grid / envelope
Systematic range and band trading, with levels sized and reset automatically.
cross-exchange arb
Captures price gaps between venues, net of fees, latency and the risk of one leg not filling.
cross-exchange mm
Quotes on one venue and hedges on a more liquid one.
funding / lp arb
Funding-rate differences, and AMM pool prices against order books.
hip-4 outcomes
Quoting and volume strategies on Hyperliquid's binary outcome markets.

Engineering notes

  • Four signing schemes behind one interface: EIP-712 / L1 actions (Hyperliquid, Aster), Ed25519 API keys (Arcus), Schnorr over ECgFp5 (Lighter). Per-key nonces and clock-skew correction.
  • Venue differences normalized: synchronous vs. asynchronous acknowledgements, client-id sizes, funding intervals, price bands, minimum sizes.
  • Orders over WebSocket on Hyperliquid and Arcus, with automatic fallback to REST when the socket drops.
  • Resilience: reconnection with backoff, resubscription, and REST resync of fills missed while disconnected.
  • Observability: latency measured per venue, method and transport; a launch journal records the git commit, versions and parameters of every run and diffs them against the previous one.
  • Control: a Telegram bot (/pf, /vol, /stats, /stop, /kill) that only answers its configured chat.
  • Tests: an offline pytest suite in virtual time that runs in seconds, simulators of Lighter and Aster written from their docs, an in-memory fake exchange; CI on GitHub Actions.
  • Research loop: strategies are tested in the C backtester before going live.

Why

Candle-based backtests say nothing about maker strategies: whether a resting order fills depends on the order flow behind it. This engine replays the full order book snapshot by snapshot and matches the strategy's orders against it, so fills, fees, inventory and drawdown can be measured before a strategy trades real money in Trador.

Design choices

  • A binary format that needs no parsing. Each 656-byte record on disk is the C struct itself. Opening a multi-gigabyte file is a memory map and a cast; a binary search on the file finds the requested time window, and only that window is mapped.
  • No look-ahead by construction. For every snapshot the engine filters bad prints, updates indicators, matches resting orders, does the accounting and liquidation check, and only then asks the strategy for quotes. The strategy never sees a book its orders were not already matched against.
  • Realistic execution. Two fill models (price must trade through, or just touch), order latency, maker and taker fees, leverage and maintenance margin. Orders that do not change keep their place in the queue.
  • Time-based indicators. EMA, SMA, volatility, microprice and imbalance are indexed on time, not on snapshot count, so irregular cadence and gaps do not bias them. A candle mode reproduces the live bot's EMA, lag included.
  • One comparable number. Results are reported as PnL per $1M traded, which compares strategies with each other and with live trading whatever the capital.
  • Pluggable strategies. A strategy is one folder and one quotes() function returning the ladder it wants; the engine knows none of them.

Tools around it

  • Downloader: 128 threads for hundreds of thousands of small S3 objects, with retry and backoff, resume, and a cached bucket listing.
  • Extractor: converts compressed JSON to the binary format, in parallel with OpenMP.
  • bin/info: checks what the engine will see: period, cadence, gaps, anomalies.
  • bin/probas: a market study with no strategy: the probability that price comes back to a given distance from its average within a horizon, used to space the order ladder.
  • Reverse mode: replaces every maker fill with a taker trade the other way, walking the visible book, to test the mirror strategy.

Problem

Before a token launches, traders want to buy or sell their future allocation. Today this happens over chat with a trusted middleman. Trench removes the middleman. Both sides lock collateral in a smart contract. At settlement, the seller delivers the real token. If the seller does not deliver, the buyer takes the seller's collateral.

I first wrote our own escrow contract. It worked, but it was limited and too custom to be audited with confidence. Code that holds user funds should not be novel, so we forked an established pre-market contract from the same niche and adapted it.

We still stopped before mainnet: no security audit had been done on our version, and we would not ask users to deposit funds into an unaudited contract.

Architecture

  • Contract (forked and adapted): collateralized bids and asks, partial fills, a settlement phase with a deadline, batch settlement, payment in native token or ERC-20. Built on OpenZeppelin upgradeable contracts with ERC-7201 namespaced storage, reentrancy guards and role-based access.
  • Indexer: a live WebSocket listener with heartbeat and reconnection, plus a recovery agent that backfills missed blocks in chunks with multi-RPC failover. Writes are idempotent, deduplicated by event hash.
  • API: Express 5 in TypeScript, wallet-signature login with session cookies, Helmet, rate limiting and input validation; run with PM2.
  • App: Angular 21 with market, trade, dashboard, leaderboard and testnet faucet pages; wallet connection through Reown AppKit.

The game

The map is generated from a seed, so any game can be replayed. Cities grow and produce units and buildings, a technology tree unlocks progress, and barbarian camps attack. A player wins by researching every technology or by holding enough territory for long enough. Games can be saved and loaded.

The terrain is deliberately fine-grained rather than smooth noise: every terrain type, and so every resource, is always close to a city, which keeps the early game moving.

The engine in core/ knows nothing about display. The same functions drive a terminal interface with ANSI colours and an SDL2 window.

Reference checker

I work on the back end of a reference checker for scientific manuscripts. My main piece is its citation-format engine.

  • Any format: users pick an existing standard (APA, AMA, IEEE…) or define their own.
  • A small template language: each citation format is described by templates. A lexer compiles them once into a tree and checks them before a format is saved; a renderer applies the tree to every reference.
  • Reformat and check: the whole reference list is rewritten to the chosen format, and each reference is validated against it.

What I work with there

  • REST APIs with FastAPI and Pydantic models
  • SQLAlchemy over a relational database
  • Background jobs with Dramatiq on Redis
  • Async HTTP clients with rate limiting for bibliographic APIs (Crossref, OpenAlex, PubMed, HAL…)
  • Fuzzy matching to compare references with the records found
  • pytest unit and integration tests run in CI; uv and ruff

Why it is here

This is not software, but it shows how I work: I set a hard goal, iterate on the design, and keep going for years until it is done properly.

It is also unlike any historical Empire bed. Period canopies hung from the ceiling; here the bed and canopy form one free-standing structure that comes apart to be moved. It is queen size where period beds were narrow singles. The plan was walnut; we chose 40-year-dried pear wood, which is much rarer.
